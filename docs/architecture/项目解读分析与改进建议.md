# Anime Tracker（追番记录）项目解读与改进建议

> 更新日期：2026-07-16
> 分析基线：Git 提交 `ee578bc`（v1.1）
> 分析范围：Web 源码、Capacitor 配置、Android 工程、云函数代理、构建与发布配置

## 一、结论摘要

Anime Tracker 已经不是只有增删改查的演示项目，而是一个具备明确使用闭环的本地优先追番工具：用户可以从 Bangumi 搜索条目、建立追番或补番记录、更新观看进度、记录单集感想、查看作品资料，并导入或导出自己的数据。

项目目前最准确的阶段判断是：**产品功能已通过原型验证，但工程质量尚未达到可持续发布标准**。

现阶段不建议继续优先增加大型功能。最值得先完成的是四件事：

1. 处理已提交到 Git 的 Android 签名文件和明文密码。
2. 统一 Web 构建与 Capacitor 打包流程，修复当前不可独立运行的 `dist` 产物。
3. 修复导入数据造成的 XSS 与数据结构崩溃风险。
4. 修正状态更新模型，解决详情页重复渲染、编辑内容回退和事件重复绑定问题。

完成以上工作后，再投入提醒、统计、数据迁移或云同步，投入产出比会更高。

## 二、项目现状解读

### 2.1 产品定位

项目服务的是“持续追踪观看过程”而不只是“收藏作品”。它包含三层价值：

- **清单层**：记录想看、在看、搁置、看完和放弃。
- **进度层**：按集推进，区分追番和补番，并按季度、星期组织内容。
- **记忆层**：总评、观后感、单集评分与单集笔记。

第三层是项目未来最有辨识度的方向。Bangumi、AniList 等平台擅长公共条目和社区评分，本项目更适合强化“属于用户自己的观看日志”。因此，产品不必急于复制大型社区，而应优先把私人记录、回顾和数据所有权做好。

### 2.2 当前功能闭环

当前 v1.1 已实现：

- 番剧新增、编辑、删除、搜索和状态筛选。
- 追番与补番两种记录模型。
- 观看进度加减和自动状态流转。
- 年份、季度分组以及折叠状态记忆。
- Bangumi 搜索、详情、封面、简介、制作信息、角色与声优展示。
- 单集评分和单集笔记。
- 文字列表与封面列表、浅色与深色模式。
- JSON 导入、导出以及 Android 原生分享。
- 启动提醒和 Android 物理返回键处理。
- 直连 Bangumi API 与腾讯云函数代理切换。

### 2.3 实际技术架构

运行代码使用的是 **Vanilla JavaScript + HTML 模板字符串 + CSS + Capacitor**，不是 React 应用。

```text
www/index.html
  ├─ js/constants.js   常量和枚举
  ├─ js/utils.js       转义、ID、日期、Toast
  ├─ js/storage.js     localStorage 持久化
  ├─ js/store.js       全局状态和 CRUD
  ├─ js/api.js         Bangumi API
  ├─ js/renderer.js    页面模板和渲染（822 行）
  ├─ js/events.js      交互与业务流程（1159 行）
  └─ js/app.js         启动和返回键
```

相较旧版分析，项目已经完成了从单 HTML 文件到多文件的第一步拆分。但这些脚本仍通过全局变量和固定加载顺序互相依赖，并没有使用 ES Module。`renderer.js`、`events.js` 和 `styles.css` 仍然过大，模块边界主要是文件边界，还没有形成稳定的领域边界。

`package.json` 声明了 React、React DOM、Zustand、TypeScript 和 React Vite 插件，但当前源码没有使用它们，也没有 `src/`、TS 配置或 JSX 入口。这部分依赖目前只增加安装体积和技术认知成本。

### 2.4 数据模型

核心记录可概括为：

```js
{
  id,
  title,
  bgmId,
  type,             // chasing | binge
  status,           // want | watching | paused | completed | dropped
  totalEpisodes,
  currentEpisode,
  rating,
  review,
  episodeNotes,     // { [episodeNumber]: { note, rating } }
  airDate,
  updateWeekDay,
  startDate,
  completedDate,
  createdAt,
  updatedAt
}
```

数据完全存于 `localStorage`，没有 schema 版本、运行时校验、迁移函数或事务。当前数据量较小时性能足够，但数据兼容性比容量更早成为问题：任何旧备份、手工修改或不完整导入都可能让渲染层直接报错。

## 三、新的项目解读

### 3.1 它更适合成为“本地优先的观看日志”

导入导出、离线可用、无需账号，这些不是临时实现，而可以成为产品立场：用户不登录也能完整使用，数据可以被用户带走。未来即使加入云同步，也应把云端设计成可选同步层，而不是使用前置条件。

### 3.2 Bangumi 应是“资料增强源”，不是运行依赖

当前作品详情、封面和角色信息在每次查看时从远程获取。网络或代理不可用时，个人记录仍在，但内容体验明显退化。更合理的模型是：

- 用户记录是本地主数据。
- Bangumi ID 是外部引用。
- 用户选中条目时保存必要的元数据快照，例如中文名、封面 URL、简介和总集数。
- 后台按 TTL 更新快照，失败时继续使用旧数据。

这样可以降低 API 请求量，也让第三方服务故障不影响核心体验。

### 3.3 “追番”和“补番”不是两个标签，而是两种工作流

追番关注今天更新什么、更新到第几集、预计何时完结；补番关注开始日期、连续观看节奏和剩余集数。后续首页、提醒和统计都应针对两种工作流分别设计，而不是只在表单里切换字段。

### 3.4 不必为了依赖已存在而立即迁移 React

旧建议把 React 迁移当成必选项，这并不准确。项目有两个合理方向：

- 保留 Vanilla JS，但改用 ES Module、JSDoc/TypeScript 检查、领域服务和可测试的纯函数。
- 当页面数量、多人协作或复杂交互继续增长时，再逐页迁移到 React。

短期更重要的是消除全局耦合、建立测试和统一构建。框架迁移本身不会自动解决状态一致性、数据校验和发布安全问题。

## 四、关键问题与风险

### P0：发布签名密钥已进入版本库

仓库同时跟踪了根目录和 `android/app/` 下的两个 `release.keystore`，两者哈希相同；`android/app/build.gradle` 中还硬编码了 `storePassword` 和 `keyPassword`，密码为弱口令。

影响：获得仓库的人可以读取签名材料。如果该密钥已用于正式分发，攻击者可能签署看起来属于同一应用的 APK；同时后续密钥轮换会受到应用商店签名策略约束。

建议：

1. 立即停止继续使用仓库中的明文密码。
2. 若使用 Google Play App Signing，轮换 upload key；若直接分发 APK，先确认现有用户升级链路再制定换钥方案。
3. 从 Git 历史中清除 keystore，并假定旧密钥已经泄露。
4. 用本机 `keystore.properties` 或 CI Secret 注入路径和密码，模板文件只保留变量名。
5. 在 `.gitignore` 中忽略 `*.keystore`、`*.jks` 和本地签名属性文件。

### P0：Web 构建产物不可独立运行

实测 `npm run build` 虽返回成功，但 Vite 对 8 个非 module 脚本逐一提示无法打包。生成的 `dist/index.html` 仍引用 `js/*.js`，而 `dist` 中并没有 `js` 目录，因此页面会在启动时找不到脚本。

与此同时，`capacitor.config.ts` 的 `webDir` 是 `www`，移动端直接复制源码而不使用 `dist`。这形成了两条不一致的发布路径。

建议二选一：

- **推荐**：把入口改为 ES Module，由 Vite 输出完整 `dist`，再把 Capacitor `webDir` 改为 `dist`；发布命令固定为 `build -> cap sync -> Android/iOS build`。
- 暂时不使用打包器：删除误导性的 Vite/React/TypeScript 配置，明确 `www` 就是发布目录，并增加静态资源完整性检查。

验收标准：在一个空目录中只复制 `dist`，通过静态服务器打开后所有核心功能可用，浏览器控制台没有 404。

### P0：导入数据可触发 XSS 或渲染崩溃

导入逻辑只检查根节点是否为数组，没有校验每条记录。标题、总评等用户数据在多个模板中直接拼入 `innerHTML`，例如卡片标题、详情标题、表单值和 textarea 内容。恶意或损坏的 JSON 可以注入 HTML，也可以让 `STATUS_CONFIG[anime.status]`、`title.toLowerCase()` 等代码报错。

建议：

- 为导入数据建立明确 schema，校验类型、枚举、数值范围、日期格式和嵌套单集记录。
- 导入前执行规范化和迁移，拒绝不可恢复的记录，并向用户展示错误明细。
- 所有插入模板的外部或用户字符串统一转义；URL 单独做协议白名单校验。
- 优先用 DOM 属性和 `textContent` 设置值，减少字符串模板中的不可信内容。
- 导入合并应优先使用稳定 ID 或 `bgmId`，标题只作为最后兜底，且需要标准化大小写与空白。

### P0：详情页状态存在重复渲染和内容回退

`updateAnime()` 自身会触发一次全页 `render()`，详情页调用方通常又执行一次 `setState()`，形成双重渲染。更严重的是，观后感自动保存只调用 `updateAnime()`，没有同步 `currentAnime`：用户停顿 500ms 后页面被旧的 `currentAnime` 重绘，可能失去焦点并显示旧文本。

建议：

- CRUD 函数只负责产生新状态和持久化，渲染由一次统一提交触发。
- 状态中只保存 `currentAnimeId`，详情始终从最新列表派生记录，避免保存对象副本。
- 输入类字段在 blur 或显式保存时提交，或做不重建 DOM 的局部更新。
- 通过事件委托绑定列表和页面交互，减少每次全量渲染后重新绑定事件。

### P1：Android 权限与网络策略过宽

Manifest 声明了 `READ_EXTERNAL_STORAGE`、`WRITE_EXTERNAL_STORAGE` 和高风险的 `MANAGE_EXTERNAL_STORAGE`，同时启用了 `requestLegacyExternalStorage`、`usesCleartextTraffic`；Capacitor 又启用了 `allowMixedContent`。当前导出逻辑使用应用目录和 Share 插件，并不需要“管理所有文件”权限，API 地址也都是 HTTPS。

建议删除不必要的存储权限和 legacy 标志，关闭明文流量与 mixed content。若确需访问用户选择的文件，应使用系统文件选择器或 Storage Access Framework。这样既降低安全面，也避免应用商店审核问题。

### P1：版本、名称和配置不一致

- `package.json` 是 `1.0.0`，Android 是 `1.1`。
- 页面与 Android 名称是 `Anime list`，Capacitor 源配置中的中文 `appName` 已出现乱码，而 Android 已同步的运行配置又是正常中文。
- 根目录和 Android 目录各保留一份相同 keystore。
- React、Zustand、TypeScript 等依赖已安装但未使用。

建议建立单一版本来源和 release 脚本，在发布时同步 npm、Android 和应用内显示版本；品牌名称也应只定义一次并在构建时注入。

### P1：API 缺少超时、取消、缓存与限流保护

`fetch` 没有超时；快速输入时旧搜索请求可能晚于新请求返回并覆盖结果；封面模式会按作品逐个请求详情；详情页每次打开都会请求作品和角色数据。云函数允许任意来源访问且没有速率限制，可能被他人消耗额度。

建议：

- 使用 `AbortController` 实现 8～10 秒超时和搜索请求取消。
- 对 429、502、503 做带抖动的有限重试。
- 为作品资料设置内存缓存和持久化 TTL 缓存，并合并进行中的相同请求。
- 云函数限制允许的路径、方法、body 大小和响应大小，设置超时、日志采样与告警；按可用条件增加网关限流。
- 生产环境减少原始响应日志，避免日志成本和意外数据暴露。

### P1：没有自动化测试和质量门禁

仓库没有 lint、单元测试、端到端测试或 CI。季度归类、导入合并、状态流转、单集记录等逻辑都依赖手工验证。

优先把下列逻辑抽成纯函数并测试：

- 观看进度与状态流转。
- 季度归类和跨年边界。
- 导入校验、迁移和合并。
- 追番提醒计算。
- Bangumi 响应解析与失败回退。

最低质量门禁建议为：`lint -> unit test -> build -> dist 静态资源检查`。Android 发布再增加 `assembleRelease` 和签名来源检查。

### P2：存储缺少 schema 版本与恢复能力

短期不必仅因“5MB 上限”立即迁移 IndexedDB；纯文本观看记录很难快速达到上限。更紧迫的是数据结构演进和恢复能力。

建议先给导出格式增加：

```js
{
  schemaVersion: 2,
  exportedAt: "...",
  appVersion: "...",
  records: []
}
```

再实现逐版本迁移、写入失败提示、自动备份和最近一次导入撤销。当封面快照、统计索引或同步队列明显增长后，再迁移到 IndexedDB。

## 五、产品改进建议

### 5.1 “今天”首页

把启动弹窗升级为稳定页面，分成：今日更新、待补进度、即将完结和最近记录。追番用户打开应用后的第一目标通常是回答“今天看什么”，不应先浏览完整档案库。

### 5.2 元数据快照与手动纠错

保存选中 Bangumi 条目的中文名、封面、简介摘要和总集数快照；允许用户解除关联或重新匹配。第三方数据不准确时，用户编辑不应被下一次刷新覆盖。

### 5.3 观看时间线与年度回顾

利用已有的 `createdAt`、`updatedAt`、进度和单集笔记，增加观看时间线、季度完成数、评分分布、年度最爱和可分享回顾。为了让统计可信，未来应把“当前状态”扩展为追加式观看事件，而不只是覆盖一个 `currentEpisode`。

### 5.4 单集笔记检索

允许搜索总评和单集笔记，并从结果直接跳到对应作品和集数。这会强化项目作为私人观看档案的价值，开发成本也低于社交功能。

### 5.5 可控的本地通知

使用 Capacitor Local Notifications 实现按星期提醒，但必须允许用户逐部开启、设置时间和静默；不要默认对所有追番开启。通知依据本地计划工作，联网时再校正条目信息。

### 5.6 云同步保持可选

只有在本地 schema、冲突策略和迁移稳定之后再加入账号系统。推荐先实现“加密备份到用户选择的位置”，再考虑实时云同步。同步冲突至少需要基于记录 ID、字段更新时间和删除标记处理，不能继续按标题覆盖。

## 六、建议实施路线图

### 阶段 A：发布止血（1～2 天）

- 处置签名密钥和明文密码。
- 修复 `dist`，统一 Capacitor 发布目录。
- 增加导入 schema 校验和统一 HTML 转义。
- 删除不需要的 Android 高风险权限和明文网络开关。
- 统一版本号、应用名称与发布脚本。

完成标准：干净环境可一次命令构建；导入恶意/损坏 JSON 不执行脚本、不导致白屏；仓库中不含签名秘密。

### 阶段 B：稳定核心（约 1 周）

- 改造状态提交，消除 `currentAnime` 对象副本和双重渲染。
- 拆出状态流转、季度归类、导入迁移和提醒计算纯函数。
- 增加单元测试、lint 和 CI。
- API 增加超时、取消、有限重试和缓存。
- 增加全局错误兜底与可恢复错误提示。

完成标准：核心纯函数有测试；连续编辑观后感不会失焦或回退；离线进入详情仍可看到已缓存资料。

### 阶段 C：提升体验（2～4 周）

- 建设“今天”首页和通知偏好。
- 增加元数据快照、重新匹配和手动纠错。
- 增加单集笔记搜索、时间线和基础统计。
- 为导出格式增加版本、迁移和自动备份。

### 阶段 D：规模化能力（按需求）

- 数据规模和查询需求出现后迁移 IndexedDB。
- 多设备需求被验证后加入可选云同步。
- 复杂页面继续增加或多人协作后，再评估 React/TypeScript 渐进迁移。

## 七、建议的近期任务清单

如果只安排下一轮开发，建议按以下顺序执行：

1. `security: rotate signing credentials and remove secrets from Git`
2. `build: convert scripts to ES modules and make Capacitor consume dist`
3. `data: validate and migrate imported backups`
4. `security: escape all rendered user content and validate remote URLs`
5. `state: replace currentAnime object with currentAnimeId`
6. `android: remove broad storage and cleartext permissions`
7. `test: cover status transitions, seasons, import merge, reminders`
8. `api: add abort, timeout, cache and proxy safeguards`

## 八、最终判断

项目的产品方向是成立的，v1.1 也已经形成完整使用闭环。其最大短板不是功能少，而是构建、密钥、数据边界和状态一致性尚未形成“可放心迭代”的底座。

下一阶段应把目标从“继续加入功能”改为“让已有功能可靠、可迁移、可发布”。完成 P0 和 P1 后，Anime Tracker 才真正具备从个人项目成长为长期维护产品的基础；届时优先强化观看日志、今日工作流和回顾能力，会比直接复制社区功能更有差异化。
